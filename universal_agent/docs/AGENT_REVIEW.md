## Общий вывод

Наиболее пригодное ядро — Aprelskiy: CV/OOF, host scoring, inner early stopping, ограниченные процессы, журнал, recovery и строгая публикация. Oleg/Rakovskiy расширяют пространство признаков и дают практичный fallback search. Ruzik добавляет особенно важную защиту от точных дубликатов и ранний полезный checkpoint. Их совместимые сильные стороны объединены; детали с утечками, неограниченным временем и принудительной обрезкой прогноза исключены.

## Aprelskiy: полный набор основных выводов

Плюсы: общий immutable CV/OOF план, проверка fingerprint/индексов/fold axis; стратификация и forward validation по наблюдаемому сдвигу времени; inner train-only eval для stopping и refit на outer train; XGBoost decoding исходных labels; bounded sparse one-hot/native CatBoost; host-controlled CPU/fit options/weights; проверка повторных recipes/code; preflight code mode; измеренные backend/parameters/importance, а не доверие названию LLM; независимый host scorer; bounded parallel workers с process groups/RSS/output caps; резерв refit с safety factor; durable event журнал и redaction; run lock, оплаченные ответы и interrupted trials восстанавливаются без повторного исполнения; small ensemble/class multipliers с separate meta assessment; атомарный submission, ID strings/order/finite checks; широкий suite и ZIP smoke из другой cwd.

Минусы: в snapshot переименованный пакет и отсутствующие runtime packaging-файлы; parser закрыт и в одном подтверждённом случае молча выбирает другую метрику; для AUC/LogLoss сохраняются labels вместо требуемых probabilities; ранний emergency файл только после профиля/диагностики/split; нет автоматической защиты от точных duplicate rows; recipe mode до интеграции ограничен параметрами и missing indicators; CV folds хранят модели, что расходует RAM/диск; диагностика большого набора до исследований может стоить дорого; RSS polling допускает краткие пики; free-code AST не доказывает безопасность/честность произвольного кода; OOF после адаптивного выбора оптимистичен, meta assessment не nested CV; резерв времени эвристический; token cap не общий денежный лимит команды; resume не гарантирован между версиями исходников; unknown ML/output formats не поддержаны. Эти ограничения не означают, что они встретятся в private данных, но должны быть видны при выборе ядра.

## Oleg: полный набор основных выводов

Плюсы: структурированные hypotheses/specifications, host scorer, внутреннее stopping, diagnostics ошибок и классов; JSON/Pydantic validation, проверка неизвестных параметров с подсказками; богатый DSL преобразований, OOF target encoding и causal lag как идеи; generic даты и текст (длина/слова/top-word counts); работа с несколькими CPU семействами; fast LightGBM chain для исследования признаков; offline playbook/random search при сбое LLM; native Ollama и OpenAI-compatible; seed averaging/greedy Caruana; safety prediction при улучшении, atomic output; fake LLM и synthetic сценарии разных типов.

Минусы: selection entity key использует target всего train до CV, поэтому выбор ключа уже подглядывает в validation; learned feature aggregations/vocab используют train+test X (transductive protocol); temporal target encoding внутри train местами random-fold, не past-only; regression predictions безусловно clip к train range; синхронное fit не имеет общего hard timeout, некоторые модели вовсе не следят за budget; fallback появляется лишь после успешного fit и отсутствует при падении всех моделей; temporal rows с NaN исключаются; 600-second default недоиспользует платформу; repeated holdout/ensemble selection не независимый nested test; unconditional seed bagging расходует финальный резерв; sample/metric conventions ограничены, MAPE использует произвольный denominator 1e-9; статический custom-code checker не sandbox; нет полноценной автоматизированной suite для всех веток; snapshot entrypoint/package/Docker ждут другое имя каталога; Dockerfile забывает pydantic. Хорошая идея языка признаков перенесена с переписанной fit-only реализацией.

## Rakovskiy: полный набор основных выводов

Плюсы общего кода — как у Oleg: declarative ops, host scoring, temporal-aware splits, диагностики, random search, seed bagging/Caruana, Ollama adapter, checkpoints. Отличительная практичная настройка — default 10200 секунд, cap10680 и три holdout folds: остаётся запас до10800, снижается шум против двух повторов. Больший бюджет полезен при наличии измеряемых новых гипотез.

Минусы общего кода — те же: supervised selection leakage entity keys; transductive aggregates; random TE внутри temporal fit; forced target-range clip; мягкий timeout; no-success -> no submission; NaN-time rows исключаются; repeated holdout и adaptively selected ensemble; затраты seed bagging; MAPE convention; custom exec и узкие parser/output formats; package/Docker layout и missing pydantic. В сравнении с Oleg отсутствуют text expansion, ранняя проверка параметров и fast feature chain; некоторые README bullets всё ещё говорят default600. Больше времени не лечит ошибки протокола и повышает риск многократного сравнения на том же validation.

## Ruzik: полный набор основных выводов

Плюсы: небольшой понятный runtime; worker с очищенным окружением, threadpoolctl, временем/RSS и process-group cleanup; independent scorer и принятие только измеренного улучшения; dummy/prior fallback и атомарный checkpoint лидеров; grouping identical features предотвращает duplicates across split; separate inner calibration для Macro F1, затем outer-train refit; неизвестные категории/пропуски/дрейф/конфликтующие duplicate labels в profile; fingerprints данных/split; compare_runs отказывается сравнивать разные split; ID/schema/order round-trip; бинарный probability output; tests, fake API и отчёты, честное отделение offline от LLM.

Минусы: metric parser выбирает первое упоминание и может оптимизировать справочную Accuracy вместо основной Macro F1; group split способен потерять редкий класс и выбросить исключение до fallback; профиль/split/hash/bundle/dummy идут до первой записи файла и вне внешнего deadline; один holdout переиспользуется многими гипотезами; fixed initial plan; API error прекращает исследование без дальнейшего generic search; probability metrics только binary/одна output column; positive class задаётся сортировкой, не условием; нет устойчивого resume; generated feature code не OS sandbox; RSS polling приблизителен; token budget не деньги команды; snapshot package/requirements артефакты отсутствуют; тест timeout не проверяет потомков/memory. Локальный отсутствующий dotenv — проблема окружения, пакет разрешён requirements.txt, это не дефект самой идеи.

## Что перепроверено экспериментально

- Aprelskiy snapshot без адаптации: 33 import errors; после восстановления ожидаемого имени 377 passed / 1 packaging failure (нет .env.example). В интеграции с настоящими обязательными файлами исходный suite: 378 passed.
- Oleg/Rakovskiy: entrypoint в snapshot не импортируется, ZIP ошибочно содержит только solution.py. После восстановления имени пакета binary synthetic у обоих: ROC-AUC 0.809388; Oleg text synthetic Accuracy0.84375. Эти локальные числа не hidden-test score и не сопоставимы с другими протоколами.
- Второй проход Oleg/Rakovskiy: fault injection всех fit -> ошибка и отсутствие submission; регрессионный prediction30 при train range[10,20] ->20; fit задержан5.2сек при лимите5сек ->фактическое превышение. Fake LLM recovery и API-unavailable ветки создали submission при наличии successful fit.
- Ruzik: 13/13 tests после восстановления имени и временных недостающих env/package fixtures. Это адаптированная тестовая копия, не исправный исходный ZIP. Adversarial parser и rare-group split ошибки воспроизведены.
- Новая интеграция отдельно проверяется по VALIDATION.md: fit-only statistics/serialization, numeric applicability, malformed DSL, duplicate-group CV, deadline, probability output и реальные публичные прогоны.

## Правила сравнения и границы полноты

Нельзя ранжировать авторов по числам из разных README: там разные holdout/CV, seeds, бюджет, offline/LLM и meta calibration. По доступному коду выбран наиболее проверяемый protocol и совместимые идеи. Полный трёхчасовой soak, системная изоляция Docker и private evaluator должны быть подтверждены отдельно. Ни один статический аудит не доказывает отсутствие всех скрытых ошибок; здесь зафиксированы весь просмотренный состав, все найденные плюсы/минусы и повторные проверки, чтобы такой вывод можно было воспроизвести.
