# Независимый аудит агента Ruzik

Аудит выполнен по snapshot `all_agents/ruzik` и платформенным условиям из `/tmp/alfa-hackathon-rules.txt`. Прочитаны все файлы snapshot, включая `baseline.py`, README, план, исходники, тесты, скрипты и материалы в `docs/`. Ссылки ниже указывают на пути и строки внутри исходного snapshot; для каталога `agent_ruzik/` номер строки относится к соответствующему модулю.

## Вывод

У Ruzik сильный и необычно хорошо измеряемый исследовательский каркас: задача профилируется, гипотезы проверяются отдельным worker-процессом, метрики считает supervisor, победитель переобучается на всём train, а результат и журнал сохраняются. Это хороший источник идей для универсального агента. По описанию и тестам публичные holdout результаты выглядят обнадёживающе, но они не подтверждены повторным запуском на полном наборе данных в этом аудите.

Snapshot имеет блокирующее несоответствие имени пакета: исходники лежат в `agent_ruzik/`, а entry point, worker, Dockerfile и упаковщик ожидают `ruzik_agent/`. Также в snapshot отсутствует `requirements-mvp.txt`, хотя упаковщик и Dockerfile его требуют. Поэтому текущий snapshot нельзя надёжно упаковать и запустить как доставляемый пакет. По указанию аудитора, тесты проверены во временной копии с восстановленным ожидаемым именем `ruzik_agent`, локальным `requirements-mvp.txt` и no-op заглушкой для отсутствующего в активном venv `python-dotenv`; оригиналы не менялись. Имена каталогов могут быть результатом переименования при подготовке snapshots, поэтому сам факт переименования следует считать проблемой текущей поставки/переноса, а не обязательно дефектом логики автора. Несовпадение уже зашито в нескольких файлах проекта и требует синхронизации при сборке.

## Карта production-кода и инструментов

- `solution.py:1-5` — единственная точка входа ZIP; импортирует CLI пакета.
- `agent_ruzik/cli.py:8-50` — контракт запуска: аргумент `task.md`, опции бюджетов, target/metric, split; загружает только локальный `.env`, не перекрывая экспортированные значения, затем запускает supervisor.
- `agent_ruzik/data.py:17-219` — поиск четырёх CSV, определение target/метрики/типа задачи, схема ответа, профиль, split и запись/проверка submission.
- `agent_ruzik/evaluation.py:7-40` — независимые метрики и диагностические отчёты для поддерживаемых регрессионных, классификационных и бинарных вероятностных метрик.
- `agent_ruzik/models.py:26-227` — валидация конфигураций, преобразования признаков, адаптеры CatBoost/LightGBM/ExtraTrees/линейной модели, внутренний калибровочный split для Macro F1.
- `agent_ruzik/llm.py:8-107` — ограниченный OpenAI-compatible интерфейс к заданным `OPENAI_*`, JSON-протокол гипотез, локальная оценка token budget.
- `agent_ruzik/runtime.py:24-257` — supervisor: резервная модель и ранняя запись ответа, очередность гипотез, worker timeout/RSS мониторинг, независимая оценка, выбор лидера, full-train refit, журналы и отчёт.
- `agent_ruzik/worker.py:16-55` — обучение/предсказание в дочернем процессе; сохраняет pickle-free массивы предсказаний и артефакт модели.
- `agent_ruzik/io.py:8-30`, `agent_ruzik/report.py:6-72` — атомарная запись JSON и автономный HTML-отчёт.
- `scripts/benchmark_public.py:9-29` — offline запуск обеих публичных задач; `scripts/compare_runs.py:7-22` — сравнение только при совпадающих fingerprint данных/split/метрики; `scripts/package_solution.py:6-24` — ZIP allowlist.
- `baseline.py:17-89` — отдельный пример MCP/LLM harness: 100 шагов, новый Python процесс на вызов, таймаут 1800 секунд. Он не вызывается из `solution.py` и не попадает в ZIP allowlist; production entry point — собственный CLI и `runtime.py`.
- `tests/test_project.py:83-277` — контракты данных, модели, API-loop, worker timeout, бинарные вероятности и ZIP. `README.md`, `RESEARCH_PLAN_RUZIK.md`, `docs/DEMO.md`, `docs/VALIDATION.md`, `docs/validation.json` описывают ограничения, протокол демонстрации и заявленные результаты.

### Платформенный контракт

В публичном кейсе платформа ожидает ZIP с `solution.py` в корне, запускает решение на каждый `task.md` отдельно, предоставляет CSV, ограничивает задачу 3 часами и задаёт API через `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL`. По умолчанию агент ищет данные рядом с Markdown и пишет `submission.csv` рядом с ним (`data.py:17-29`, `runtime.py:94-100`). Выход сохраняет ID и порядок столбцов из шаблона и перечитывает CSV перед атомарной заменой (`data.py:194-219`). Это соответствует публичному описанию интерфейса при корректно собранном ZIP. `baseline.py` — не этот production entry point, а тестовый harness, что важно не перепутать при интеграции.

## Сильные стороны

1. **Ответ появляется до исследования.** `runtime.py:119-128` немедленно после подготовки данных сохраняет dummy baseline; если API, worker или финальный refit падают, более поздняя итерация не стирает уже записанный рабочий CSV. Улучшения пишутся только после независимой проверки метрики.
2. **Ресурсные границы и завершение процессов продуманы.** `runtime.py:24-70` задаёт отдельную process group, ограничивает время и суммарный RSS процесса с потомками и убивает группу на timeout/error. Переменные секретов не передаются worker (`runtime.py:38-45`). Лимиты потоков задаются и через env, и через `threadpoolctl` (`worker.py:35`).
3. **Нет утечки ID/target в признаки.** Target и ID выводятся из словаря, train/test схемы проверяются, ID исключены из `features` (`data.py:64-85`). Подготовка признаков обучается внутри модели на training части; пропуски и неизвестные категории поддерживаются (`models.py:80-113`, `154-195`).
4. **Сильная схема для дубликатов и F1.** При доле повторяющихся строк выше 1% split группирует хеши признаков, чтобы идентичные наблюдения не разделялись между train и validation (`data.py:175-186`). Для Macro F1 можно подобрать classwise веса вероятностей на внутренней калибровочной части training fold, затем модель переобучается на всём training fold; внешний validation остаётся оценкой (`models.py:126-151`).
5. **Измеримость и воспроизводимость.** Split и входы fingerprint-ятся, эксперименты сериализуются, кандидат не заменяет лидера без улучшения, а comparison tool отказывается сравнивать разные данные/разбиения (`runtime.py:105-118, 205-226`; `scripts/compare_runs.py:11-18`).
6. **Полезная диагностика.** Профиль содержит пропуски, кардинальность, неизвестные категории, дубликаты, сдвиг числовых средних, дисбаланс и конфликты меток одинаковых строк (`data.py:122-153`). Отчёт показывает Macro F1 по классам, ошибки регрессии и важности (`report.py:15-42`).
7. **Хорошая обработка результата.** Проверяется допустимость предсказаний, ID и порядок после CSV round-trip; временный файл заменяет целевой лишь после проверок (`data.py:194-219`). Worker сохраняет строковые метки без pickle (`worker.py:16-23`).
8. **Достаточная локальная инженерная дисциплина.** Запланированы allowlist ZIP, сравнение честных запусков, API mock, а README прямо отделяет offline демонстрацию от настоящей работы Qwen (`README.md`, `tests/test_project.py`, `docs/DEMO.md`).

## Недостатки и риски

### Блокирующие для текущей поставки

- **Несогласованные имена импортируемого пакета.** `solution.py:2`, `agent_ruzik/runtime.py:44`, `Dockerfile:8` и `scripts/package_solution.py:11` обращаются к `ruzik_agent`, но каталог в snapshot называется `agent_ruzik/`. При запуске исходного дерева `solution.py` не импортируется; worker не стартует; контейнер не найдёт путь COPY; ZIP не положит ни одного `.py` модуля в архив. Это подтверждено инвентаризацией всех файлов. Нужна единая выбранная структура и одинаковое имя в entry point, worker, Dockerfile, пакетировании и тестах.
- **ZIP allowlist ссылается на отсутствующий файл.** `scripts/package_solution.py:9-10` всегда читает `requirements-mvp.txt`, но такого файла нет в snapshot. В `Dockerfile:5-6` он также обязателен. Поэтому `package()` на чистом snapshot завершится `FileNotFoundError` до создания пригодного ZIP. В тестовом runtime-copy файл был временно создан лишь для возможности исполнить suite; это не считается проверкой оригинального архива.
- **Локальная установка тестовой среды неполна.** `cli.py:42` безусловно импортирует `dotenv`; в заданном активном `.venv` `python-dotenv` отсутствует. Запуск тестов в восстановленной копии без заглушки сразу провалил 5 CLI интеграционных тестов с `ModuleNotFoundError`. В requirements организаторов пакет присутствует, поэтому для платформенного контейнера это не доказанный runtime-дефект при корректной установке, но snapshot не включает свой `requirements-mvp.txt`, а README обещает именно такой самостоятельный набор.

### Ошибки определения задачи и покрытие приватных сценариев

- **Парсер метрики выбирает первое упоминание, а не основную метрику.** `data.py:88-100` сужает поиск до предполагаемой секции, но затем берёт самое раннее совпадение любого regex. На искусственной задаче с текстом `Справочно Accuracy, основная метрика Macro F1` агент выбрал `accuracy`. Для формулировок, где сначала приведены справочные метрики, это меняет оптимизацию и итоговый выбор модели. Нужен приоритет выражений «основная метрика», явный словарь метрик либо отказ при неоднозначности.
- **Auto split не определяет временную/групповую природу задачи.** `data.py:156-186` использует random/stratified split, кроме случая заметных точных дубликатов; time/group разбиение доступно лишь через CLI overrides. Private задача, требующая временного или субъектного holdout, может получить утечку даже без ошибок. В headless-платформенном режиме ручной override может быть недоступен. Это также признано README в разделе ограничений.
- **Потеря редкого класса при group split завершает задачу ошибкой.** После выбора `GroupShuffleSplit` функция проверяет присутствие всех классов в обеих частях (`data.py:187-188`) и выбрасывает исключение вместо повторной попытки/стратифицированного группового выбора. В граничной проверке с повторяющимися признаками, где единственная группа редкого класса попала в одну сторону, получено `ValueError: Разбиение потеряло классы`. В production это происходит до записи fallback submission (`runtime.py:105`, fallback начинается только на строке 127), так что часть небольших приватных датасетов останется вообще без файла ответа.
- **Универсальность ограничена одним типом supervised-таблиц и одним выходным столбцом.** `data.py:12-14, 76-85, 101-117` допускает только список из 9 метрик, один target, один response column; ROC AUC/LogLoss и binary F1 требуют ровно два класса. Ranking, forecasting с временным протоколом, multi-output, multi-class probability output и неизвестные метрики не реализованы. README это честно признаёт; значит универсальность в приватной части не гарантируется.
- **Идентификация положительного класса жёстко сортировочная.** `data.py:46-51` всегда считает последний `sorted(classes)` positive class. README прямо предупреждает, что если текст задачи задаёт другую положительную метку, контракт надо расширить. Это корректно для ряда кодировок, но скрытая бинарная задача с семантическим positive label может получить неверные вероятности.

### Честность валидации и AutoResearch

- **Много экспериментов оцениваются по одному и тому же holdout.** Это повышает риск адаптивного переобучения: LLM выбирает последующие гипотезы по результатам той же validation, а максимум 12 trials всё равно подгоняется к ней (`runtime.py:148-225`). Cross-validation/подтверждающий split в коде нет; README и `docs/DEMO.md` сами называют это ограничением. Идея полезна как MVP, но метрика лидера может быть оптимистична.
- **Правило безопасности generated feature code только частично статическое.** `models.py:26-47` блокирует часть импортов/имен/атрибутов, а `models.py:96-100` затем исполняет код через `exec` внутри worker. Линтер не доказывает отсутствие межстрочных статистик и не является OS sandbox; запрет подгонки на `test` находится главным образом в системном промпте (`llm.py:17-23`). `README.md` справедливо указывает, что это не изоляция недоверенного кода. Значит неожиданный/вредоносный код может нарушить экспериментальные предпосылки, зависнуть/потребить ресурсы, а валидация по строкам не гарантирует соблюдение запрета использовать распределение validation/test.
- **Оценка стоимости API локальная, а не командная.** `llm.py:56-95` ведёт токены только в рамках одного процесса; `max_tokens` не привязан к тарифу и общему лимиту команды в 600 рублей. Запуски задач стартуют отдельно, а общего persistent ledger или механизма распределения суточного бюджета нет. README отдельно признаёт, что локальный лимит не заменяет командный учёт. При трёхчасовом private запуске количество запросов может превысить доступный денежный лимит.
- **Начальные модели — фиксированный план, а не вывод из профиля.** `runtime.py:73-88, 140-144` всегда начинает с фиксированного набора семейств, а offline candidates также хардкодятся. LLM включается только после них. Это быстрый baseline, но не даёт агенту выбирать валидатор, семейство или стратегию по предметной структуре до первых затрат.
- **Ошибка/плохой ответ LLM может остановить цикл до max trials.** Форматная ошибка пишет `llm_error` и повторяет цикл, но исключение транспорт/API в `runtime.py:171-175` прекращает дальнейшее исследование; это оправданно бережёт время и сохраняет CSV, однако устойчивость далее зависит от базовых экспериментов.

### Защита от дедлайна и ограничения доказательств

- **Дедлайн контролируется вокруг worker, но не до fallback.** `runtime.py:91-128` начинает таймер, затем читает и профилирует все данные, считает split/fingerprint, сериализует целый bundle и обучает/оценивает dummy до первой записи ответа. На предусмотренных публичных наборах это, вероятно, коротко; на резко больших или патологических приватных данных запуск может быть остановлен платформой до первого submission. Нужен ранний валидный выход/worker cutoff на подготовительных стадиях или прогрессирующая запись.
- **Измерение RSS дискретное.** `runtime.py:49-62` опрашивает дерево процессов раз в 150 мс; короткий пик может не попасть в отчёт (сам `docs/VALIDATION.md` это оговаривает). Это мониторинг, не строгая гарантия потолка памяти; контейнерный лимит платформы остаётся последней защитой.
- **Timeout тест не покрывает потомков.** `tests/test_project.py:231-239` проверяет микроскопический timeout до импорта worker и факт остановки процесса, но не создаёт дочерний процесс/проверку очистки process tree и не проверяет memory limit. Реализация `killpg` выглядит разумно, однако заявленный process-tree cleanup отдельно тестом не доказан.
- **Публичные цифры в документах не воспроизводились здесь.** `docs/VALIDATION.md` и `docs/validation.json` утверждают 13 тестов, две полные публичные задачи, CSV и метрики, но сами данные отсутствуют в snapshot. Docker build и живой Qwen API прямо отмечены как непроверенные. Поэтому указанные Macro F1 0.629994 и RMSE 44.406363 — записанные авторами offline holdout результаты, а не независимо подтверждённые значения данного аудита.

## Проверки аудитора и граничные случаи

- Изолированная копия переименована из `agent_ruzik/` в ожидаемое тестами `ruzik_agent/`; тестовые оригиналы оставлены read-only. При исходной копии без заглушки первый запуск suite дал 5 падений из-за `ModuleNotFoundError: dotenv` в этой локальной среде. С временной no-op заглушкой `dotenv.load_dotenv`, созданной только в `/tmp/alfa-audit-ruzik/stubs`, и временным `requirements-mvp.txt` suite: **13/13 тестов пройдены за 22.535 с**.
- Прошли тесты контрактов CSV/ID, неизвестных категорий и четырёх модельных адаптеров, split точных дубликатов, API mock с recovery, malformed JSON feedback, API 500 fallback, timeout worker, бинарных вероятностей, ZIP/запуска из другой cwd. ZIP тест в копии проверил воспроизводимый архив и запуск с восстановленным каталогом модуля; он не проверяет оригинальный snapshot без добавленного requirements-файла.
- Дополнительный граничный тест метрики воспроизвёл ошибочный выбор `accuracy` вместо `macro_f1` при явной формулировке «справочно Accuracy, основная метрика Macro F1».
- Дополнительный group split тест подтвердил, что редкий класс может потеряться в одной части и вызвать исключение до появления fallback CSV.
- Полные public benchmarks в этом аудите не запускались: task data отсутствуют в read-only каталоге агента. Валидация Docker/Qwen также не воспроизводилась; документы автора указывают, что они не проверены.

## Идеи для универсального агента

Рекомендую перенести: (1) немедленный рабочий fallback с атомарным улучшением, (2) отдельный worker без секретов плюс process-group cleanup, timeout, RSS и лимит потоков, (3) supervisor, который сам рассчитывает metric и принимает только подтверждённого лидера, (4) фиксированные split и входные fingerprint для воспроизводимого сравнения, (5) профиль категорий/пропусков/дрейфа/дубликатов до гипотез, (6) group split по одинаковым строкам признаков, (7) внутреннюю настройку решения для Macro F1 и refit на полном training fold, (8) повторную проверку submission после CSV round-trip, (9) журнал гипотез, ошибок и измерений с отчётом, (10) адаптацию финального резерва по измеренному времени лидера.

Не переносить без усиления: один фиксированный holdout на все адаптивные trials; heuristic parser основной метрики; random split по умолчанию для возможных временных/групповых данных; локальный token budget вместо общего учёта денег; только prompt-level запрет на leakage generated-кода; и только дискретный RSS sampling как средство гарантии памяти.
