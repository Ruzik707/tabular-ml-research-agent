# Независимый аудит решения Aprelskiy

Дата проверки: 21.10.2026. Проверяемый snapshot: `all_agents/aprelskiy`; временные изменения для тестового запуска вносились только в копию `/tmp/aprelskiy-src`. Это аудит по доступному дереву кода и тестам, а не утверждение об исчерпывающей проверке всех runtime-сценариев.

## Вывод

У агента сильное исследовательское ядро: хост сам строит CV-план, запускает и оценивает модели, журналирует решения, держит запас под финальный fit и умеет восстановить работу после прерывания. По конструкции это заметно надёжнее простого LLM-скрипта. Но проверенный snapshot в текущем виде нельзя запустить или упаковать штатным способом: код ожидает пакет `automl_agent`, а в дереве лежит `aprelskiy_agent`; кроме того, отсутствуют обязательные файлы упаковки. Без исправления доставки качество экспериментов не имеет значения.

Критичные подтверждённые замечания:

1. **Блокирующая ошибка запуска/доставки в данном snapshot.** `solution.py:9,19` импортирует `automl_agent`, subprocess в `automl_agent/agent.py:387,750` запускает `python -m automl_agent.worker`; в snapshot пакета с таким именем нет, фактический каталог называется `aprelskiy_agent/`. На временной копии без тестового alias `python solution.py --help` завершается кодом 1 с `ModuleNotFoundError: No module named 'automl_agent'`; чистый `pytest` дал 33 ошибки сбора по той же причине. Это наблюдение про конкретную раскладку snapshot, не приписываемое авторскому алгоритму.
2. **Упаковка также блокируется независимо от namespace.** Нет `.env.example` и `requirements-mvp.txt`; `Dockerfile:11,14` требует их, `scripts/package_solution.py:14,22–32` требует их и директорию `automl_agent`. Тест реальной упаковки подтвердил `FileNotFoundError` на `.env.example`. README описывает другой layout (`automl_agent/`, файлы зависимостей), чем лежит в проверенном дереве.
3. **Парсер метрики может выбрать неверную цель оптимизации.** `_METRIC_PATTERNS` в `aprelskiy_agent/data.py:32` ищет подстроку `accuracy`; фактическая `_metric_from_text("Primary metric: balanced accuracy")` вернула `accuracy`. `config.py:95`, `data.py:320–338` и `evaluation.py:142–190` не поддерживают balanced accuracy. Значит распознанная задача будет оцениваться стандартной accuracy; при CLI-переопределении `--metric balanced_accuracy` argparse отвергнет запуск. Это важно для универсального private набора, хотя неизвестно, присутствует ли такая метрика в скрытых задачах.
4. **Финальный fit не имеет гарантии завершения по резервной оценке времени.** В `agent.py:748–752` он всё равно ограничен `remaining - write_margin` через `run_process`; при недооценке fit возможен timeout, а затем останется ранее записанный кандидат/аварийный submission. Резерв адаптируется по измеренному времени и коэффициенту безопасности, но это эвристика, а не гарантия. Это риск качества результата при трёхчасовом дедлайне, а не отдельное доказательство, что timeout отсутствует.

## Сильные стороны

- **Хост владеет оценкой.** LLM предлагает гипотезу/recipe, но оценку считает `evaluation.py`; выбор лучшего результата игнорирует ложный статус success и неfinite метрики (`agent.py:22–25`). Это отделяет модель от подсчёта score.
- **CV разложен на независимые роли.** Хост заранее строит и сохраняет split plan; worker видит train fold и validation fold без validation target, а host scorer после выполнения сверяет OOF-артефакты. При временной стратегии есть forward/group разбиение. `training.py` делает inner split только внутри внешнего train для early stopping; финальный worker обучается на полном train.
- **Нет прямой утечки test labels в диагностиках.** `data_diagnostics.py` анализирует train/test признаки, включая adversarial domain classifier, но не получает истинные test target. Это допустимая transductive диагностика при локально доступных тестовых признаках.
- **Ограниченная поверхность recipe.** Recipe нормализуется, параметры ограничены диапазонами/типами, семейство и preprocessing контролирует хост; код рецептного режима синтезирует runtime, а не исполняет произвольное LLM-решение. Code mode остаётся гибче и поэтому рискованнее.
- **Бюджетированная оркестрация.** Максимум времени валидируется до 10 800 секунд, CPU × параллельность ограничены 8, суммарный memory allowance конфигурируется до 28 GB. Для refit оставляется первоначальный резерв и обновляемая оценка по времени измеренного обучения (`budgeting.py:10–13` и `agent.py:321–343`). Сразу публикуется аварийный/базовый вариант (`agent.py:834–836` и ранее в run setup), поэтому принудительный timeout не обязан оставить пустой файл.
- **Изоляция и ограничение процесса.** `runtime.py:181–...` задаёт wall timeout, ограничивает объём захваченного вывода, мониторит RSS дерева и завершает дерево процессов; `worker.py` исполняется отдельно. Это хороший слой отказоустойчивости, хотя RSS sampling не эквивалентен жёсткой cgroup-границе.
- **Устойчивое восстановление.** `journal.py` дописывает и синхронизирует события; agent берёт run lock, сверяет fingerprint данных/split, сохраняет оплаченный LLM-ответ и помечает неопределённый in-flight запуск, чтобы не запустить его повторно без необходимости. Тесты проверяют paid-response recovery и concurrent resume.
- **Безопасная публикация.** `evaluation.py` сверяет точные колонки/порядок/число строк/ID/целевые значения и finite predictions, пишет результат атомарно. Базовый submission сохраняется до исследования.
- **Честная оговорка по CV selection.** README и итоговый отчёт предупреждают, что адаптивный отбор по OOF завышает оценку; postprocessing тоже выбирается на OOF и потому не является независимой внешней оценкой.
- **Хороший audit trail.** JSONL журнал, decision log, профили, split manifest, версии пакетов, model details и experiment artifacts помогают проверить поведение после запуска.

## Риски и конкретные дефекты

### Блокирующие / высокие

**R1. Namespace и доставочная раскладка не совпадают.** В чистом snapshot `solution.py:9,19` ожидает `automl_agent`, worker-исполнение в `agent.py:387,750` тоже запускает `automl_agent.worker`; каталог называется `aprelskiy_agent/`. Повторяемая проверка без alias: `python solution.py --help` → rc=1 / `ModuleNotFoundError`. Это потенциально вызвано переименованием каталога при формировании snapshot, поэтому в оценке авторской идеи следует отделять его от core-кода.

**R2. Штатный ZIP и Docker build не собираются из snapshot.** `scripts/package_solution.py:14,22–41` ждёт `.env.example`, `requirements-mvp.txt`, `automl_agent/`; файлов и каталога нет. `Dockerfile:11,14–15` копирует отсутствующие файлы. После временного package alias тест упаковки всё равно упал на `.env.example`. До финальной интеграции требуется согласовать имя пакета и список реально поставляемых файлов; одной локальной символьной ссылки недостаточно, так как packager намеренно запрещает ссылки (`:26–27,33–37`).

**R3. Неполный/неверный парсер private метрик.** Подтверждённый пример: `_metric_from_text("Primary metric: balanced accuracy")` → `accuracy`; отклонённый CLI override: `--metric balanced_accuracy` с argparse invalid choice (`config.py:95`). В core поддерживаются RMSE/MAE/R2 и набор классификационных F1/accuracy/AUC/log-loss (`data.py:320–338`, `evaluation.py:142–190`), хотя `postprocessing.py` имеет отдельную balanced-accuracy ветку (`:39–41,286–330`). Из-за несогласованности результата оценивание обычной accuracy вместо balanced accuracy даст систематически неверный selection. Расширять можно только когда формат платформы допускает такую метрику; универсальный fallback должен скорее явно сообщать unsupported metric, чем молча подменять её.

**R4. Reserve снижает, но не устраняет риск незавершённого final fit.** `budgeting.py` прогнозирует длительность по прошлому измерению, при отсутствии наблюдения использует долю общего времени. В `agent.py:748–752` process timeout всегда равен фактически оставшемуся времени после write margin. На новых данных/другой нагрузке оценка refit может промахнуться; `agent.py:763–768,862–874` фиксирует ошибку/пропуск и сохраняет предыдущий submission. Это делает fallback полезным, но финальная модель на всех train-данных и качество может не успеть получить ожидаемый апгрейд. Нужны smoke-тесты медленного финального worker-а и явно проверенный бюджетный профиль.

### Средние / универсальность

**R5. Закрытый metric parser ограничивает переносимость.** Помимо balanced accuracy, `data.py:26–35` и CLI закрывают метрики на небольшом наборе; нет, например, median absolute error, MAPE, Cohen's kappa, PR-AUC или precision@k. Это не утверждение о том, что hidden tasks обязательно используют их; это покрытие только тех метрик, которые известны в интерфейсе/условии. Важнее, что неизвестная метрика не представляется как unsupported на уровне общего evaluator protocol.

**R6. Отбор и postprocessing оцениваются на повторно используемых OOF.** На CV-хосте внешний OOF значительно лучше простого train-fit оценивания, однако гиперпараметры/recipe, выбранный среди многих trials, и пороги постобработки выбраны по тем же OOF-ответам. CV-метрика победителя оптимистична; README это раскрывает. При коротком runtime вложенная nested CV на каждый кандидат слишком дорогая, но можно сохранить отдельные audit folds или ограничить число решений по OOF.

**R7. Ресурсный контроль приблизительный для памяти.** `runtime.py` опрашивает RSS дерева процесса; между опросами возможен короткий пик, который ОС/container может обработать раньше, чем parent убьёт процесс. Валидация конфигурации лимитов (`config.py`) не равно kernel-enforced cgroup quota. Требуется учитывать запас на host-process, параллельные workers, библиотеки и память CV-артефактов.

**R8. Ollama как провайдер не соответствует целевому runtime без настройки.** `config.py:97–102` по умолчанию выбирает OpenAI-compatible endpoint, но при `AUTOML_PROVIDER=ollama` использует localhost и `qwen3.5:9b`. Это хороший dev/offline adapter, однако условия платформы дают endpoint определённой модели и отключают интернет; локальный Ollama нельзя считать доступным или разрешённым runtime по умолчанию. Для submissions необходимы корректные platform env vars и проверка совместимого OpenAI endpoint. В README описан локальный Ollama для разработки, не доказательство, что production использует его.

**R9. Время profiling/diagnostics вычитается из общего бюджета.** Профиль и dataset diagnostics запускаются до research (`agent.py:804–824`), а CV diagnostics дополнительно стоят CPU/RAM/диск. Это разумные данные для стратегии, но на больших/широких данных предварительный profiling может съесть существенную долю бюджета. Нужен тест на крупном синтетическом датасете с жёстким таймером; доступные тесты не доказывают three-hour soak.

**R10. Резюме совместимости надо сохранять в контексте смены snapshot.** Resume защищён fingerprint-ом данных/split, но перед интеграцией важно включить в resume fingerprint пакет кода/recipe schema/версии runner. Текущие тесты проверяют изменившиеся train данные и восстановление оплаты, но не апгрейд/замену source между вызовами. Это риск сценария обновления во время разработки, не установленный дефект текущего одиночного submission.

## CV и утечки: вывод аудита

По прочитанной цепочке `validation.py → cv_worker.py → training.py → evaluation.py` прямой утечки validation target в estimator не обнаружено: split indices и feature-target артефакты формируются хостом; внешний worker получает fold-specific validation features и не получает labels в модельный fit; метки остаются у host scorer. Early stopping использует отдельный внутренний split только из внешнего train fold. Финальное обучение получает весь train после выбора модели. Domain classifier получает train/test **features** без test target. Параметры `target` удаляются из feature frame и проверяются при построении TaskSpec.

Остаточный статистический риск — adaptive overfitting на повторно используемом OOF и диагностических результатах. Также временная CV безопасна только если обнаружены правильная временная колонка и сортировка/группировка действительно соответствуют зависимости; автоматическое распознавание времени остаётся эвристическим. Отсутствие явной утечки в просмотренном коде не заменяет независимое тестирование на данных конкурса.

## Лучшие идеи для universal_agent

1. **Оставить разделение control plane и model plane:** LLM выдаёт гипотезу/DSL, хост сам фиксирует split, запускает worker, считает метрику и выбирает победителя.
2. **Перенести CV-план как immutable artifact** с fingerprint и проверкой alignment OOF indices; не позволять эксперименту самому выбирать validation rows.
3. **Оставить внутреннюю validation только внутри outer train fold** для early stopping и аналогичных решений; final refit обучать на полном train с сохранённым выбранным числом итераций.
4. **Сохранить резерв финального fit и emergency submission**, но логировать отдельные measured/estimated fit costs и явно считать финализацию завершённой только после валидации атомарно записанного submission.
5. **Использовать durable event journal и восстановление оплаченного ответа**, включая run lock и fingerprint; это редкая полезная инженерная идея при дорогих LLM-вызовах.
6. **Предпочесть fit-only feature DSL и ограниченный каталог recipe** свободной генерации кода; code mode оставить как sandboxed escape hatch. DSL должен задавать преобразования, fit options и estimator, не доступ к validation labels.
7. **Сохранить адаптивный profiling как дешёвые budgeted диагностики:** schema/type/duplicate/group/time/drift checks и adversarial CV как предупреждение о shift, не как утечку target.
8. **Сохранить строгий submission validator и атомарную публикацию** плюс отдельный end-to-end package smoke test из ZIP в unrelated working directory.
9. **Нормализовать метрики в одном contract/evaluator catalog.** Парсер условия, CLI, objective direction, train metric и evaluator должны импортировать один реестр; неизвестная метрика должна быть явной ошибкой/режимом деградации, а не близкой подстановкой.
10. **Изоляция worker-а должна ограничивать все ресурсы согласованно:** стеночное время, число потоков, память процесса/контейнера, stdout/stderr, диск/число артефактов; RSS polling — дополнительная защита, не жёсткая квота.

## Границы достоверности

Сильные результаты тестов подтверждают локальные контракты и искусственные сценарии, но не качество на двух публичных и двух private задачах. В доступном snapshot namespace и packaging несогласованы; все тесты логики после временного alias относятся к коду, который можно импортировать, а не к готовому submission archive. Выводы об unknown hidden metrics сформулированы как риски переносимости. Полнота аудита разумно высока для production-модулей, однако не абсолютна: не проводился прогон на платформе, крупном реальном наборе данных, всех сочетаниях task conventions и трёхчасовая soak-проверка.
