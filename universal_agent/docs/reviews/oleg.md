# Аудит `oleg`

## Итог

Внутри агента есть хорошая исследовательская архитектура: метрику считает хост, гипотезы LLM заданы спецификациями, предусмотрен резервный эвристический цикл и сохраняется аварийный submission. Олеговские изменения добавляют полезные generic-механизмы — признаки из короткого свободного текста, проверку имён гиперпараметров и отдельный быстрый этап поиска признаков. Однако исходный каталог в текущем виде не запускается и собирает ZIP только с `solution.py`: точка входа ищет `agent`, а код лежит в `agent_oleg`. В проверяемом snapshot это блокирует запуск. Само несовпадение фактовое; доступные артефакты не позволяют установить, возникло ли оно в авторском репозитории или при snapshot/переименовании пакета, поэтому авторство дефекта не приписываю.

## Карта файлов и различия

- `solution.py` — CLI и ограничение бюджета; `agent_oleg/runner.py` — исследовательский цикл, расписание времени, refit и ансамбль.
- `agent_oleg/task.py` — поиск CSV и target, разбор задачи/метрики, профилирование; отличие Oleg — `_expand_text`.
- `agent_oleg/models.py` — LightGBM/CatBoost/XGBoost/ExtraTrees/linear и подготовка данных; отличие Oleg — `valid_params`.
- `agent_oleg/researcher.py` — LLM и offline-плейбук; отличие Oleg — ранняя проверка параметров с подсказкой.
- `agent_oleg/diagnostics.py`, `features.py`, `llm.py`, `metrics.py`, `schemas.py`, `validation.py`, `__init__.py` совпадают побайтно с Rakovskiy. Их общая логика разобрана ниже.
- `tests/make_synthetic.py` генерирует бинарную и multiclass классификации, временную регрессию, текст, high-cardinality target encoding и большой MAPE-набор; `tests/fake_llm_server.py` отдаёт битый JSON, затем валидный/ошибочный proposal и пишет последний запрос.
- `scripts/package.py` собирает ZIP; `Dockerfile` описывает локальный образ; `README.md` описывает запуск и заявленные локальные результаты; `docs/EXPERIMENTS.md` — журнал экспериментов. Служебный `.DS_Store` не является частью решения.

## Критические ошибки

1. **Платформенный ZIP не содержит пакет, а прямой запуск падает.** В `all_agents/oleg/solution.py:16` вставляется корень, но импорт на строке 18 — `from agent.runner import Agent`. Фактический пакет называется `agent_oleg/`. Упаковщик ищет только `ROOT / "agent"` (`all_agents/oleg/scripts/package.py:13`); Dockerfile также делает `COPY agent ./agent` (`all_agents/oleg/Dockerfile:10`). В исходной копии `solution.py --help` завершился `ModuleNotFoundError: No module named 'agent'`; `package.py` успешно, без предупреждения, создал ZIP размером 1 KB только из `solution.py`. Это стоп-блокер.
2. **Dockerfile не устанавливает обязательный Pydantic.** Он ставит numpy/scipy/pandas/sklearn и три бустинга (`all_agents/oleg/Dockerfile:6`), но схемы импортируют `pydantic` (`all_agents/oleg/agent_oleg/schemas.py:16`). После исправления пути пакет всё равно не импортируется в образе, если Pydantic не установлен отдельным слоем. При этом `requirements.txt` содержит `pydantic==2.10.6`.
3. **Разбор задач и метрик уже, чем заявленная универсальность.** Парсер распознаёт ограниченный список названий и эвристически определяет тип задачи (`all_agents/oleg/agent_oleg/task.py:55`, `all_agents/oleg/agent_oleg/metrics.py:45`). Например, неизвестная метрика приводит к `ValueError` (`all_agents/oleg/agent_oleg/metrics.py:65`); precision/recall, balanced accuracy, Brier, ranking, multilabel и unsupervised не поддержаны. Скрытая задача с другим evaluator-критерием может аварийно завершиться либо оптимизировать proxy. Поддержаны CSV supervised classification/regression, а не произвольный ML-кейс.

## Сильные стороны

- **Проверяемый AutoResearch, а не исполнение свободного кода LLM.** LLM предлагает JSON-спецификации, Pydantic ограничивает схему, а хост сам запускает модель и считает score (`all_agents/oleg/agent_oleg/researcher.py:56`, `all_agents/oleg/agent_oleg/runner.py:159`). На сбой/отсутствие LLM есть offline-плейбук (`all_agents/oleg/agent_oleg/runner.py:298`, `all_agents/oleg/agent_oleg/researcher.py:207`). Это снижает риск выдуманного LLM-скора и позволяет получить результат без API.
- **Валидация учитывает очевидный временной сдвиг.** Если test целиком позже train, выбираются последовательные временные holdout-фолды; иначе — повторные стратифицированные holdout для классификации (`all_agents/oleg/agent_oleg/validation.py:15`, `all_agents/oleg/agent_oleg/validation.py:53`). Обучение внутри модели использует отдельный внутренний early-stopping split, не host-valid (`all_agents/oleg/agent_oleg/models.py:131`). Это уменьшает прямую утечку на валидацию.
- **Диагностика даёт основания для следующего эксперимента.** Отчёт считает train/valid-разрыв, регрессионные хвосты и сегменты, per-class F1 и confusion pairs (`all_agents/oleg/agent_oleg/diagnostics.py:39`). Это соответствует циклу AutoResearch лучше, чем безусловный перебор параметров.
- **Generic target encoding для повторяющихся сущностей.** Ключи ищутся по train/test coverage и однородности таргета, а encoding внутри обучающей части делается out-of-fold; для времени есть causal lag (`all_agents/oleg/agent_oleg/features.py:167`, `all_agents/oleg/agent_oleg/features.py:203`, `all_agents/oleg/agent_oleg/features.py:249`). Идея переносимая, если таблица содержит повторные сущности; она не зашита на названия признаков здания или сетевого потока.
- **Тесты проверяют нестандартные контракты, а не только один happy path.** Генератор включает binary probability, multiclass probability columns, даты, свободный текст, high cardinality и крупный набор (`all_agents/oleg/tests/make_synthetic.py:34`); fake LLM проверяет неверный ответ, ошибочную операцию и custom feature (`all_agents/oleg/tests/fake_llm_server.py:14`).

## Уникальные удачные идеи Oleg

- **Текстовая колонка автоматически превращается в generic признаки длины, числа слов и частот top-50 слов** вместо категориального признака с почти уникальным значением (`all_agents/oleg/agent_oleg/task.py:142`). Проверка на текстовой синтетике в копии дала host-valid accuracy 0.84375; признаки `review_text__len` и частоты слов появились в профиле модели. Это ощутимое расширение по сравнению с Rakovskiy, но простая bag-of-words-гипотеза: русский/английский текст ок, семантика, n-граммы и редкие словоформы не моделируются; детектор пропускает короткие тексты и зависит от первых 2000 строк.
- **Параметры модели проверяются до обучения, включая те, что библиотеки молча игнорируют** (`all_agents/oleg/agent_oleg/models.py:324`, `all_agents/oleg/agent_oleg/researcher.py:47`). Это ловит опечатки и возвращает LLM вероятные варианты имени; полезная защита от «успешного» эксперимента, где заданный параметр не повлиял на модель.
- **Сильные признаки сначала проверяются на быстрой LightGBM-цепочке, затем переносятся на лучшее семейство** (`all_agents/oleg/agent_oleg/runner.py:242`). Это ослабляет зависимость поиска признаков от стартового CatBoost/медленного семейства. У Rakovskiy этого кода нет.

## Честная оценка поиска, ансамбля и времени

Offline random search задаёт случайные 1–3 параметра из фиксированных сеток и чередует текущее семейство с альтернативными бустингами (`all_agents/oleg/agent_oleg/researcher.py:273`). Это разумный fallback для исчерпания гипотез, но не адаптивный Bayesian search: распределение узкое и ручное, шаги могут быть дубликатами после нормализации, а каждый выбор оценивается на тех же host-фолдах. Следовательно, это источник кандидатов, не гарантия поиска глобально хороших параметров.

Seed averaging способен уменьшить дисперсию финального бустинга, и в журнале приведены локальные улучшения на публичных задачах (`all_agents/oleg/docs/EXPERIMENTS.md:98`). Но кандидат выбирается по единственному seed на holdout; повторное обучение тремя seed не устраняет шум выбора модели. Ансамбль Caruana отбирается по validation-предсказаниям, затем проверяется на других фолдах (`all_agents/oleg/agent_oleg/runner.py:411`). Это полезная защита от явного переобучения ensemble weights, но повторные random holdout имеют перекрывающиеся train-наборы, а временные фолды вложены по времени; проверка не полностью независима от этапа отбора. Вес члена пропорционален числу его повторов в Caruana, а не отдельной калибровке.

Критично соблюдать budget/checkpoint: платформа останавливает процесс через 3 часа и требует готовый файл заранее (правила кейса, стр. 7, 17). CLI Oleg по умолчанию отводит 600 секунд и 2 фолда (`all_agents/oleg/solution.py:24`, `all_agents/oleg/solution.py:29`); это безопасно по времени, но оставляет большую часть разрешённых трёх часов неиспользованной. При этом класс `Agent` имеет тот же 600/2 default (`all_agents/oleg/agent_oleg/runner.py:31`). Safety submission после каждого улучшения и атомарная запись — сильный checkpoint-подход (`all_agents/oleg/agent_oleg/runner.py:203`, `all_agents/oleg/agent_oleg/runner.py:515`). README корректно описывает классический default, но оставляет нерешённым выбор платформенного времени; Ollama 4B приводится только как локальный эксперимент, сами авторы пишут, что сравнение с разрешённой Qwen 27B организаторов ещё нужно сделать (`all_agents/oleg/README.md:78`, `all_agents/oleg/README.md:88`).

## Предметные риски и проверки

- Авторазбор даты делает календарные части и timestamp, свободный текст — слова; это обобщается на разные имена столбцов, но семантические отношения/единицы из `data_dictionary.csv` не превращаются в предметные признаки (`all_agents/oleg/agent_oleg/task.py:116`, `all_agents/oleg/agent_oleg/task.py:142`). На данных зданий/сетевого трафика хорошие target keys получаются из структуры повторов, однако искать все комбинации признаков за 30 секунд и проверять purity на доступных метках — эвристика; высокая purity может быть случайной для редких групп.
- Temporal detector требует test полностью правее train на одном числовом/дата столбце (`all_agents/oleg/agent_oleg/validation.py:15`). При смешанном, групповом или сдвинутом по распределению test будет обычный random holdout. Target encoding во временном режиме делает OOF разбиение обучающих строк случайным (`all_agents/oleg/agent_oleg/features.py:235`), поэтому признаки обучающих строк могут использовать таргеты более поздних строк; оценка host-valid напрямую не получает их метки, но temporal train/valid feature-generation режим отличается.
- LLM реализована через OpenAI-compatible HTTP и нативный Ollama API, без SDK и с ограничением общего токенного счётчика (`all_agents/oleg/agent_oleg/llm.py:21`). Ollama не входит в requirements как исполняемый сервис, а локальные результаты на Qwen 3.5 4B не доказывают качество на кейсовой Qwen 27B; эти ограничения явно отмечены в README. Платформенные переменные соответствуют baseline, сетевой вызов будет работать лишь при доступности выданного API из контейнера.
- У Oleg реестр различий между CLI/README согласован (600 с, 2 folds), но для лимита 3 часа такой default недоиспользует ресурс. В README также указаны локальные цифры, не подтверждённые нами и явно помеченные авторами как локальная validation (`all_agents/oleg/README.md:47`).

Проверки выполнены в копии внутри audit worktree. До обхода несовпадения имени пакета `solution.py --help` падал, а ZIP содержал только entrypoint. Для проверки ML-логики в копии создан каталог `agent/` из `agent_oleg/` (исходники не менялись): binary ROC-AUC прошёл end-to-end (0.809388, probability submission, 3-seed refit); текстовый synthetic прошёл (accuracy 0.84375); `discover` распознал multiclass `log_loss`/колонки вероятностей, а датированный набор выбрал 3 temporal folds. После alias ZIP содержал entrypoint и все 12 файлов пакета. Docker не собирался; отдельный Dockerfile-анализ выше выявил недостающий Pydantic. Полноценные прогоны больших/high-cardinality сценариев, 3-часовой deadline и реальный API Ollama/Qwen в этой проверке не выполнялись. Воспроизводимые окружения сверены с заданным `requirements.txt` (в частности, Pydantic 2, LightGBM, CatBoost, XGBoost); baseline интерфейс сверялся с `all_agents/ruzik/baseline.py` — `OPENAI_*`, task path и требование записать предсказания рядом с задачей.


## Второй критический проход: runtime

Эти замечания одинаково относятся к Oleg и Rakovskiy: четыре проверенных модуля (`features.py`, `models.py`, `validation.py`, основная логика `runner.py`) совпадают, кроме перечисленных в основной части различий веток.

1. **CV-оценка entity key использует метки validation до начала экспериментов.** `setup()` сначала строит split, затем вызывает `find_entity_keys(self.train, ..., self.task.target, ...)` на полном train (`all_agents/oleg/agent_oleg/runner.py:97`, `all_agents/rakovskiy/agent_rakovskiy/runner.py:97`). Функция читает весь target, оценивает purity каждого ключа и возвращает ключ для `target_encode` (`all_agents/oleg/agent_oleg/features.py:259`, `all_agents/oleg/agent_oleg/features.py:280`, `all_agents/oleg/agent_oleg/features.py:291`). Offline-плейбук затем проверяет выбранный ключ на тех же host folds. Это supervised feature selection до CV: validation labels влияют на выбор гипотезы, а тот же validation оценивает её качество. OOF-encoding внутри `apply_target_ops` не устраняет этот более ранний leakage.
2. **Регрессионные predictions всегда обрезаются по train target range.** Oleg (`all_agents/oleg/agent_oleg/runner.py:524`) и Rakovskiy (`all_agents/rakovskiy/agent_rakovskiy/runner.py:491`) применяют `np.clip(pred, y.min(), y.max())` к любому regression submission. Это запрещает предсказывать новый максимум/минимум, даже если test продолжает временной тренд. Проверка функции `write_submission` в обеих копиях: искусственный prediction 30 при train-target диапазоне [10, 20] превращён в 20. Для RMSE это может систематически ухудшить будущий тест; clamp должен зависеть от задачи/метрики или быть гипотезой, а не безусловной postprocessing-операцией.
3. **Гарантированный safety-файл не гарантирован, если все fit-ы падают.** Первый safety CSV пишется только после успешного эксперимента и только если он лучше текущего (`all_agents/oleg/agent_oleg/runner.py:199`, `all_agents/rakovskiy/agent_rakovskiy/runner.py:197`). Если baseline не обучился, `best` остаётся пустым; `finalize()` выбрасывает `RuntimeError` (`all_agents/oleg/agent_oleg/runner.py:475`, `all_agents/rakovskiy/agent_rakovskiy/runner.py:442`), а `run()` вызывает его вне `try` исследовательского цикла (`all_agents/oleg/agent_oleg/runner.py:539`, `all_agents/rakovskiy/agent_rakovskiy/runner.py:506`). В копиях я заставил каждый `Model.fit` выбрасывать ошибку: обе версии завершились `ни один эксперимент не завершился успешно`, submission отсутствовал. Обещание README о submission «при любых сбоях» поэтому сильнее реальной гарантии.
4. **Валидационная метрика MAPE может отличаться от evaluator при нулевых target.** Реализация делит абсолютную ошибку на `1e-9` для нуля (`all_agents/oleg/agent_oleg/metrics.py:29`); `sklearn.metrics.mean_absolute_percentage_error` использует машинный epsilon. Если private task содержит нули, внутренний scorer может ранжировать кандидатов иначе, чем evaluator. Это условный дефект: формат hidden evaluator в PDF не задаёт, какой вариант MAPE используется.
5. **Временной split пропускает строки с пустым/нечисловым временем из всех validation folds.** Маски используют `values < threshold` и `values >= threshold`; NaN не попадает ни в fit, ни в valid (`all_agents/oleg/agent_oleg/validation.py:70`, `all_agents/rakovskiy/agent_rakovskiy/validation.py:70`). Это меняет оцениваемую популяцию относительно полного train, хотя при нормальном поле времени доля может быть нулевой. К тому же выбор temporal mode требует, чтобы почти все значения времени были парсируемы и test целиком позже train (`all_agents/oleg/agent_oleg/validation.py:15`).

**Таймауты — soft deadline, а не жёсткое прерывание fit.** `TimeBudget` только хранит wall-clock deadline (`all_agents/oleg/agent_oleg/models.py:35`). LightGBM, CatBoost и XGBoost проверяют его callback-ами между boosting iterations (`all_agents/oleg/agent_oleg/models.py:171`, `all_agents/oleg/agent_oleg/models.py:200`, `all_agents/oleg/agent_oleg/models.py:219`); текущая итерация, подготовка данных, scoring и диагностика не прерываются. ExtraTrees и linear принимают `budget`, но вообще не читают его (`all_agents/oleg/agent_oleg/models.py:242`, `all_agents/oleg/agent_oleg/models.py:255`). Все `model.fit` вызываются синхронно в main thread (`all_agents/oleg/agent_oleg/runner.py:176`); отдельного process/future watchdog вокруг fit нет. В тесте обеих копий я задержал ExtraTrees `.fit` на 5.2 с при `seconds=5`: вызов вернулся через 5.21 с на `MainThread`. Для ExtraTrees/linear долгое обучение может пересечь и внешний 3-hour cutoff; RAK budget cap сам по себе этого не предотвращает. LLM, напротив, работает в daemon thread и ограничена `Future.result(timeout=...)` (`all_agents/oleg/agent_oleg/runner.py:298`, `all_agents/oleg/agent_oleg/runner.py:313`); HTTP-запросы и retry могут продолжаться в этой нити после отказа ждать, но daemon не удерживает выход процесса.

**Train+test feature aggregates проверены.** `setup()` соединяет train и test в `all_X` (`all_agents/oleg/agent_oleg/runner.py:84`); затем `apply_ops` считает частоты по объединённым строкам (`all_agents/oleg/agent_oleg/features.py:88`), а group mean/rank — по целой объединённой группе (`all_agents/oleg/agent_oleg/features.py:91`). На probe `key=[a,b,a]`, `x=[0,20,100]` получили для обоих агентов частоту `a=2/3`, а среднее группы `a=50`, включая вклад последней строки test. Это transductive использование только X, без меток; в кейсе test features выдаются агенту, поэтому само по себе оно не является label leakage. Но такая метрика валидирует режим с доступными validation/test covariates, а не строго train-only preprocessing. Target encoding отделён и использует OOF для train-части (`all_agents/oleg/agent_oleg/features.py:203`).

**Recovery и работа без API проверены без ключа.** При `OPENAI_API_KEY` и внешнего API не было: обе версии с unset `OPENAI_MODEL/OPENAI_API_KEY/OPENAI_BASE_URL` выбрали offline-плейбук, получили ROC-AUC 0.809388 на synthetic binary и создали финальный submission.
